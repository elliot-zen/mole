# write-product-spec

为用户需求和功能点写 `PRODUCT.md` 规格；

## 概览

产品规范应使期望行为足够明确，使智能体能够正确实现并避免回归。请从用户的视角描述该功能——用户所看到、所做、体验到的内容，以及必须成立的不变性。不包含实现细节（内部类型、状态布局、模块边界、数据流、算法）

将规格写到 `specs/<id>/PRODUCT.md`, `id` 可以为
- 简短的 `kebab-case` 风格名称 (e.g. specs/vertical-tabs-hover-sidecar/PRODUCT.md)

书写的文档使用中文，必要术语使用英文;

## 在生成`PRODUCT.md`之前

- 就这个计划的方方面面毫不留情地采访我，直到我们达成共识。沿着设计树的每个分支，逐一解决决策之间的依赖关系。对于每个问题，提供你的推荐答案。每次只问一个问题，等待每个问题的反馈后再继续。
- 同时问多个问题是令人困惑的。
- 如果一个问题可以通过探索代码库来回答，那就去探索代码库吧。在我确认我们达成共识之前不要写入 `PRODUCT.md`;

## 文档结构

**必要的部分**

- 概述: 1-3段话描述需求和期望结果； 
- 行为: 这部分是`PRODUCT.md`的核心，详尽描述该 Spec 的工作原理，其他部分尽量保持简略，避免重复的部分；参照以下 [[#行为]] 

**可选的部分**

- 问题: 在该需求不明确时才会包含； 
- 目标/非目标: 在需求范围模糊时才会包含;

请不要包含验证，成功标准以及测试的部分，他们应该在 `TECH.md` 中书写；

## 行为

该部分需要足够详细，使作者能够根据它写出技术规格文档；无需猜测或重新推导出需求意图；
至少包括:
- 默认行为和用户流程的`happy path`;
- 每一个用户可见状态及其之间的转换;
- 所有用户输入及其响应方式；
- 空状态，错误状态，加载/待处理状态和取消;
- 边缘情况(Edge Case)
